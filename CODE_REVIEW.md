# Ревью перехода на 0.3.0

Дата: 22 октября 2026 года.

Проверены весь исходный код компонента, Composer-конфигурация, контракт SDK 0.6.0,
документация и тесты. Компонент состоит из одного PHP-класса.

## Исправлено

* Унаследованный `TinkoffClientsFactory::create($token)` вызывал `new static($token)`,
  хотя конструктор компонента принимает конфигурационный массив Yii2.
  Добавлен совместимый метод `create()`, сохраняющий позднее статическое связывание.
* Конструктор явно принимает `array`; проверены конфигурация через `Yii::createObject()`,
  токен, пользовательское/стандартное имя приложения, пустая конфигурация,
  `create(null)`, создание подкласса и отклонение неизвестной настройки.
* Пример README проверяет статус RPC перед обращением к ответу, содержит импорты
  моделей; дублирующий запрос удалён.
* Удалено разрешение dev-зависимостей. Нижняя граница Yii2 2.0.55 включает
  исправления PHP 8.5 из 2.0.54 и исправление безопасности из 2.0.55.

## Оставшиеся замечания

* **P2 — публичные настройки после создания компонента не синхронизированы с SDK.**
  Присваивание `$component->apiToken = 'new-token'` меняет публичное свойство,
  но запросы продолжают использовать защищённый `_api_token`, и кеш клиентов не
  сбрасывается. Обратное расхождение возникает при использовании `setApiToken()`:
  запросы используют новый токен, публичное свойство хранит прежний.
  Аналогично устроено `appName`. Это прежнее поведение; для смены настроек
  используйте методы SDK `setApiToken()` / `setAppName()`.
  При отдельном исправлении следует сохранить поддержку `null` в конфигурации.
* **P2 — SDK 0.6.0 теряет пользовательское имя приложения при создании клиентов.**
  Его `TinkoffClientsFactory::getBaseConnectionOptions()` вызывает
  `ClientConnection::getOptions($this->_api_token)` без `_app_name`.
  Поэтому переданное в конфигурации имя сохранено фабрикой, но метаданные
  запроса содержат стандартное имя SDK. Исправление требуется в SDK либо
  отдельным переопределением этого метода в обёртке. Файлы `vendor` не исправлялись.

## Проверки и ограничения

* `composer validate` (Composer 2.10.3) — успешно; единственное предупреждение
  касается явного поля `version`, сохранённого по требованию задачи.
* `composer update --prefer-lowest --prefer-stable --prefer-dist --no-interaction
  --ignore-platform-req=ext-grpc` — успешно, с целевой `config.platform.php=8.5.12`.
  Установлены SDK 0.6.0, Yii2 2.0.55, protobuf 5.36.2, grpc/grpc 1.82.0;
  Composer выбрал HTMLPurifier 4.19.0 с учётом блокировки уязвимых версий.
  Сгенерированный lock-файл использован для аудита, в библиотеку не включён.
* `composer audit --locked` — опубликованных Composer advisories не найдено.
  Это не аудит JavaScript-ассетов Yii2: их версии и безопасность следует
  контролировать в конечном приложении.
* Синтаксис `src/TinkoffInvestApi.php` и `tests/compatibility.php` — успешно
  на временном автономном PHP 8.5.8.
* Проверки конструктора/фабрики из теста прошли с реальными Yii2 2.0.55 и SDK 0.6.0
  на PHP 8.5.8 через отдельный загрузчик. Проверки платформы и создания gRPC-клиента
  в этом частичном прогоне исключены; штатный тест не изменён для обхода требований.
* Полный прогон `composer test` и проверка целевой платформы **не подтверждены**:
  локально отсутствует PHP, временный CLI имеет версию 8.5.8 без gRPC,
  Docker Desktop после запуска и перезапуска не получает ответ от своей VM
  (`192.168.65.7:2376: no route to host`, API 500 / timeout).
  `composer check-platform-reqs` ожидаемо сообщает недостаточную версию PHP
  и отсутствие ext-grpc. Настройки платформы и штатный автозагрузчик сохранены.
* Добавлена CI-матрица PHP 8.5.12 / ext-grpc 1.83.1: минимальные и последние
  разрешённые зависимости, проверка платформы, аудит, синтаксис и полный тест.
  Удалённый CI в рамках этой задачи не запускался.

Реальные RPC и торговые операции не выполнялись.
